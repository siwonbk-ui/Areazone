# ระบบปรับปรุงข้อมูล NAT CAT อัตโนมัติ (n8n + GitHub Actions)

## ภาพรวม

```
n8n (ทุกวัน 07:00)
  └─ เรียก CKAN API ของ ปภ. + กรมพัฒนาที่ดิน   ← เบามาก (JSON ไม่กี่ KB)
     └─ เทียบกับ state ที่เก็บใน repo
        ├─ ไม่เปลี่ยน → จบ (ไม่เปลืองอะไรเลย)
        └─ เปลี่ยน → สั่ง GitHub Actions
                      └─ ดาวน์โหลดข้อมูลจริง → คำนวณใหม่ → commit data_updated.js
                         └─ GitHub Pages เผยแพร่เว็บเวอร์ชันใหม่อัตโนมัติ
                            └─ n8n อ่านผลการรัน → AI สรุป → แจ้งทีม
```

**ทำไมไม่ให้ n8n ประมวลผลเองทั้งหมด** — ไฟล์ต้นทางรวมกันราว 40 MB ต่อรอบ และตรรกะการรวมข้อมูล/จัดชั้นเป็นงานที่ต้องได้ผลเหมือนเดิมทุกครั้ง จึงให้ n8n ทำหน้าที่ "เฝ้าดูและสั่งงาน" ส่วนการคำนวณจริงอยู่ใน `pipeline/pipeline.py` ที่รันบน GitHub Actions

**AI ทำอะไรในระบบนี้** — เขียนสรุปผลให้คนอ่านเท่านั้น (ว่าชุดข้อมูลไหนเปลี่ยน ผลการรันสำเร็จหรือไม่) **ไม่ได้ประมวลผลตัวเลขหรือกำหนดสีความเสี่ยง** เพราะงานนั้นต้องตรวจสอบย้อนกลับได้และให้ผลเดิมทุกครั้ง

## สิ่งที่ต้องเตรียม

### 1. ฝั่ง GitHub

1. อัปโหลดทุกไฟล์ในโฟลเดอร์ `github-updated` ขึ้น repo (รวมโฟลเดอร์ `.github` และ `pipeline`)
2. เปิด **Settings → Actions → General → Workflow permissions** เลือก **Read and write permissions** แล้ว Save
   (เพื่อให้ workflow commit ไฟล์ข้อมูลกลับเข้า repo ได้)
3. เปิด GitHub Pages: **Settings → Pages → Deploy from a branch → `main` / `(root)`**

เท่านี้ระบบก็ทำงานเองได้แล้ววันละครั้ง (cron ใน `update-data.yml`) แม้ไม่ต่อ n8n

### 2. สร้าง GitHub Personal Access Token (สำหรับให้ n8n สั่งงาน)

**Settings → Developer settings → Personal access tokens → Fine-grained tokens**
- Repository access: เลือกเฉพาะ repo นี้
- Permissions: **Actions = Read and write**, **Contents = Read-only**
- คัดลอก token เก็บไว้

### 3. ฝั่ง n8n

1. **Import workflow**: เมนู `⋯ → Import from File` เลือก `natcat-daily-update.json`
2. **สร้าง Credential** ชนิด **Header Auth**
   - Name: `Authorization`
   - Value: `Bearer <token ที่ได้จากข้อ 2>`
   - แล้วผูกกับ 2 โหนด: *สั่ง GitHub Actions ให้สร้างข้อมูลใหม่* และ *เช็คผลการรัน*
3. **ค่า repo ใส่ไว้ให้แล้ว** — ไฟล์นี้ตั้งค่าเป็น `siwonbk-ui/Areazone` branch `main` เรียบร้อย
   ไม่ต้องตั้ง n8n Variables (ถ้าย้าย repo ค่อยแก้ URL ใน 3 โหนดที่ขึ้นต้นด้วย `github`)
4. **ผูก credential ของโมเดลภาษา** ที่โหนด *โมเดลภาษา* (ค่าเริ่มต้นเป็น OpenAI — เปลี่ยนเป็นผู้ให้บริการอื่นได้)
5. **ต่อช่องทางแจ้งเตือน** แทนโหนด *แจ้งทีม (ต่อ Slack / LINE / Email ที่นี่)*
   - เนื้อความอยู่ใน `{{ $json.text }}` จากโหนด AI

## ทดสอบก่อนเปิดใช้จริง

```bash
python pipeline/pipeline.py --check
```
บอกว่าแหล่งข้อมูลเปลี่ยนหรือยัง โดยไม่ดาวน์โหลดไฟล์ใหญ่

```bash
python pipeline/pipeline.py --force --out data_updated.js
```
สร้างข้อมูลใหม่ทั้งหมด (ครั้งแรกใช้เวลาประมาณ 2–5 นาที)

ใน n8n กด **Execute Workflow** เพื่อรันทดสอบ — ครั้งแรก state ยังไม่ตรงกันจึงจะสั่ง rebuild เสมอ

## ข้อควรรู้เรื่องความถี่ของข้อมูล

ข้อมูลต้นทางจริง ๆ **ไม่ได้เปลี่ยนทุกวัน**:

| ชุดข้อมูล | ความถี่ที่เผยแพร่จริง |
|---|---|
| ปภ. — วาตภัย / อุทกภัย / ดินโคลนถล่ม | ปีละครั้ง (ราวเดือน พ.ค.) |
| กรมพัฒนาที่ดิน — น้ำท่วม/แล้งซ้ำซาก | ปีละครั้ง |
| กฎกระทรวงแผ่นดินไหว | เปลี่ยนเมื่อมีการแก้กฎหมาย |

การเช็กทุกวันจึงมีประโยชน์ในแง่ "รู้ทันทีที่หน่วยงานปล่อยข้อมูลปีใหม่" มากกว่าการได้ตัวเลขใหม่ทุกวัน — และเพราะเช็กด้วย metadata ขนาดไม่กี่ KB จึงแทบไม่มีต้นทุน

## จุดที่ควรมีคนดูแล

- **เกณฑ์แบ่งสีคำนวณใหม่อัตโนมัติทุกครั้งที่ build** (เปอร์เซ็นไทล์ 95/85/65 ของการกระจายตัว) ทำให้การเพิ่มข้อมูลปีใหม่ไม่ทำให้พื้นที่สีแดงเฟ้อขึ้นเอง — แต่แปลว่า**สีของบางอำเภออาจขยับได้เมื่อข้อมูลปีใหม่เข้ามา** ค่าเกณฑ์ที่ใช้จริงในแต่ละรอบถูกบันทึกไว้ใน `buildInfo.cutoffs` ของ `data_updated.js` และแสดงในปุ่ม "แหล่งข้อมูล" ของหน้าเว็บ
- ถ้าหน่วยงานเปลี่ยนโครงสร้างไฟล์ (เคยเกิดมาแล้วหลายปี) pipeline อาจอ่านคอลัมน์ไม่เจอ ควรดูสรุปผลการรันที่ AI ส่งมาทุกครั้งที่มีการ rebuild
- ควรให้ผู้รับผิดชอบตรวจข้อมูลก่อนนำไปใช้ตัดสินใจจริงทุกครั้งที่มีการปรับปรุงใหญ่
